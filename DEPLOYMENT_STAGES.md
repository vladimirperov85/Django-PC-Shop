# 📝 РЕЗЮМЕ СЕССИИ 4 (15.08.2026) — НАСТРОЙКА PostgreSQL

## Что сделали
База данных PostgreSQL создана и настроена, `.env` на сервере заполнен, Django успешно подключился к базе.

## Подробно по шагам

1. **Запуск PostgreSQL** — `systemctl start postgresql` + `systemctl enable postgresql` (автозапуск). Проверка через `pg_isready` → accepting connections. Статус `active (exited)` — нормально: сервис-обёртка запускает основной процесс и завершается.

2. **Создание базы и пользователя** — через `sudo -u postgres psql`:
   - `CREATE DATABASE shop_db` — пустая база-контейнер для таблиц
   - `CREATE USER shop_user WITH PASSWORD '...'` — учётка для Django
   - `ALTER ROLE` × 3 — кодировка utf8, изоляция read committed, timezone Europe/Moscow
   - `GRANT ALL PRIVILEGES ON DATABASE shop_db TO shop_user` — полные права на базу

3. **Создание .env на сервере** — `nano /root/PC_Shop/.env`. Заполнен:
   - Новый SECRET_KEY (сгенерирован отдельно для сервера, без префикса `django-insecure-`)
   - `DEBUG=False` (продакшен)
   - `ALLOWED_HOSTS=139.100.238.148,localhost,127.0.0.1`
   - `DB_ENGINE=postgres` + параметры подключения к PostgreSQL
   - HTTPS-настройки (пока False)

4. **Исправление опечатки** — в `.env` были `SESSION_COKIE_SECURE` и `CSRF_COKIE_SECURE` (одна буква O). Исправлены на `SESSION_COOKIE_SECURE` и `CSRF_COOKIE_SECURE` (две буквы O, как в Django). Без исправления настройки молча не работали бы при включении HTTPS.

5. **Проверка подключения** — `python manage.py shell -c "from django.db import connection; connection.ensure_connection(); print('DB connection OK')"` → `DB connection OK`. Django успешно подключился к PostgreSQL под учёткой shop_user.

## Что поняли/запомнили (важные уроки)

- **`systemctl status` с `active (exited)`** — нормально для PostgreSQL в Ubuntu: сервис-обёртка запускает основной процесс и завершается со статусом SUCCESS.
- **`pg_isready`** — простая проверка, что PostgreSQL принимает подключения. Быстрее и надёжнее, чем разбор статуса systemctl.
- **`ALTER ROLE ... SET`** — устанавливает параметры по умолчанию для конкретной роли (не для всей системы). Django рекомендует: utf8, read committed, правильный timezone.
- **`GRANT ALL PRIVILEGES ON DATABASE`** — права выдаются только на конкретную базу. Принцип минимальных привилегий: shop_user не имеет доступа к другим базам.
- **Опечатки в именах переменных .env — «тихая мина»** — Django не падает, просто использует default. Если default совпадает с желаемым значением — проблема невидима. Проявляется только при попытке изменить значение.
- **`django-insecure-` префикс** — не часть ключа, а метка-предупреждение от `startproject`. `get_random_secret_key()` возвращает чистый ключ без префикса.
- **Аутентификация Django↔PostgreSQL — автоматическая** — Django берёт учётные данные из `.env` и подключается к базе без интерактивного ввода пароля.

## Что сделали

## ⚠️ Ключевое отличие от гайда (важно понимать)

Гайд `DEPLOYMENT_GUIDE.md` писался под сценарий с обычным пользователем в `/home/<ваше-имя>/PC_Shop` и сокетом в папке проекта (`project.sock`). Если бы сокет лежал в `/root/PC_Shop`, Nginx (работает от `www-data`) не смог бы к нему обратиться → **502 Bad Gateway**.

**Решение:** сокет кладём в системную папку `/run/gunicorn.sock` (доступна всем), а в unit-файле указываем `Group=www-data` — это даёт Nginx «пропуск» к сокету.

## Подробно по шагам

1. **Создание unit-файла** — `nano /etc/systemd/system/gunicorn.service` (содержимое — в следующем разделе).

2. **Запуск и автозапуск**:
   - `systemctl daemon-reload` — systemd перечитал unit-файлы и узнал про новый сервис
   - `systemctl start gunicorn` — запуск прямо сейчас (⭐ сначала забыли выполнить — статус был `inactive (dead)`, вспомнили и запустили)
   - `systemctl enable gunicorn` — включение автозапуска при загрузке системы (создался симлинк в multi-user.target.wants/)
   - `systemctl status gunicorn` → **active (running)**, 3 воркера, сокет `/run/gunicorn.sock`

3. **Проверка прав на сокет** — `ls -la /run/gunicorn.sock` → `srwxrwxrwx 1 root www-data ...` — группа `www-data` на месте, Nginx сможет обратиться к сокету.

4. **Перезагрузка сервера и проверка автозапуска**:
   - Заметили сообщение `*** System restart required ***` (осталось от обновлений Сессии 1) — перезагрузились в конце сессии
   - `reboot` → подождали ~30 сек → `ssh root@139.100.238.148` → `systemctl status gunicorn` → **active (running)**, Main PID 545 (маленький номер = сервис стартовал одним из первых при загрузке)
   - Автозапуск подтверждён: никто не запускал Gunicorn руками, а он работает

## 📄 Файл `/etc/systemd/system/gunicorn.service` (итоговое содержимое)

```ini
[Unit]
Description=gunicorn daemon для PC_Shop
After=network.target

[Service]
User=root
Group=www-data
WorkingDirectory=/root/PC_Shop
EnvironmentFile=/root/PC_Shop/.env
ExecStart=/root/PC_Shop/.venv/bin/gunicorn --workers 3 --bind unix:/run/gunicorn.sock django_password_generator.wsgi:application
ExecReload=/bin/kill -s HUP $MAINPID
KillMode=mixed
TimeoutStopSec=5
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

## Пояснения к настройкам (шпаргалка на будущее)

- **`[Unit]`** — «визитка» сервиса: `Description` — имя в статусе, `After=network.target` — запускаться после поднятия сети.
- **`User=root`** — от чьего имени запускать процесс (у нас root, т.к. проект в /root).
- **`Group=www-data`** — группа процесса. Именно она даёт Nginx (пользователь www-data) доступ к сокету. Это «пропуск» для веб-сервера.
- **`WorkingDirectory=/root/PC_Shop`** — рабочая папка (аналог `cd` перед запуском). Относительно неё Django ищет файлы.
- **`EnvironmentFile=/root/PC_Shop/.env`** — подгрузить переменные окружения из `.env`. **Без этой строки сервис не знал бы** SECRET_KEY, DB_NAME, ALLOWED_HOSTS и т.д.
- **`ExecStart=`** — команда запуска:
  - `/root/PC_Shop/.venv/bin/gunicorn` — полный путь к Gunicorn из виртуального окружения (просто `gunicorn` systemd может не найти)
  - `--workers 3` — 3 рабочих процесса (для 1–2 ГБ RAM нормально)
  - `--bind unix:/run/gunicorn.sock` — слушать unix-сокет в /run (наш «почтовый ящик» для Nginx)
  - `django_password_generator.wsgi:application` — модуль wsgi.py, объект application — стандартный вход Django для WSGI-серверов
- **`ExecReload`** — «перезагрузка на лету» через сигнал HUP (без остановки сервиса).
- **`KillMode=mixed` / `TimeoutStopSec=5`** — порядок завершения: сначала мягко (SIGTERM), затем принудительно через 5 сек.
- **`PrivateTmp=true`** — изолировать временную папку (безопасность).
- **`[Install]` / `WantedBy=multi-user.target`** — сервис включается при обычной (неграфической) загрузке системы.

## Команды systemctl, которые запомнили

| Команда | Что делает |
|---------|-----------|
| `systemctl daemon-reload` | Перечитать unit-файлы (после создания/изменения сервиса) |
| `systemctl start gunicorn` | Запустить сервис прямо сейчас |
| `systemctl enable gunicorn` | Включить автозапуск при загрузке |
| `systemctl status gunicorn` | Показать состояние сервиса |
| `systemctl restart gunicorn` | Перезапустить (полезно после изменений кода/.env) |

## Что поняли/запомнили (важные уроки)

- **`start` ≠ `enable`**: `start` запускает сейчас, `enable` включает автозапуск на будущее. Обе команды нужны. Если выполнить только `enable` — сервис зарегистрирован, но не работает (`inactive (dead)`).
- **Папка /root закрыта (права 700)** — только root может в неё заходить. Поэтому сокеты для Nginx нельзя класть в /root — нужно системное место (/run).
- **`Group=www-data` — мост к Nginx**: сокет, созданный процессом группы www-data, доступен пользователю www-data (от него работает Nginx).
- **Маленький PID после перезагрузки = ранний старт**: PID 545 означает, что сервис поднялся в начале загрузки системы.
- **`*** System restart required ***`** — напоминание, что после apt upgrade нужно перезагрузить сервер (применяются обновления ядра). Не ошибка, не блокирует работу — но перезагрузиться стоит.
- **Проверка автозапуска = перезагрузка**: единственный достоверный способ убедиться, что enable работает — перезагрузить сервер и посмотреть, поднялся ли сервис сам.

## Пояснения к конфигу (шпаргалка на будущее)

- **`listen 80;`** — слушать стандартный HTTP-порт. Браузер по умолчанию обращается к 80, поэтому `http://IP` работает без указания порта.
- **`server_name 139.100.238.148;`** — отвечать на запросы к этому IP. Если будет домен — поменять на домен.
- **`location = /favicon.ico`** — точное совпадение (`=`). Отключает логирование запросов к иконке (мусор в логах).
- **`location /static/` + `alias`** — Nginx отдаёт CSS/JS **сам**, без Django. `alias` заменяет `/static/` на реальный путь `/root/PC_Shop/staticfiles/`. Важно: `alias`, а не `root` — иначе Nginx искал бы `/root/PC_Shop/static/` (а у нас `staticfiles/`).
- **`location /media/` + `alias`** — то же для картинок товаров. Nginx отдаёт их сам.
- **`location /`** — всё остальное (HTML-страницы). `include proxy_params` — подгрузить стандартные заголовки прокси. `proxy_pass http://unix:/run/gunicorn.sock` — передать запрос в Gunicorn через сокет.
- **Логика разделения:** статика и media — Nginx отдаёт сам (быстро, без Python). Динамика — Gunicorn/Django (генерирует HTML). Это классическая схема Django+Nginx+Gunicorn.

## Что поняли/запомнили (важные уроки)

- **`alias` vs `root` в Nginx** — `root` добавляет путь к URI (`/static/` + `/static/` = двойной путь), `alias` заменяет URI на реальный путь. Когда URL и папка на диске не совпадают (`/static/` → `staticfiles/`) — нужен `alias`.
- **`reload` vs `restart`** — `reload` перечитывает конфиг без остановки (текущие соединения не рвутся), `restart` полностью перезапускает процесс. Для применения конфига — `reload`.
- **`nginx -t` — безопасная проверка** — проверяет синтаксис, но не применяет изменения. Если конфиг сломан, сервер продолжает работать со старым. Всегда проверять перед `reload`.
- **403 Forbidden = нет прав на чтение** — не путать с 404 (файл не найден). 403 значит: файл есть, но Nginx не может его прочитать из-за прав.
- **`chmod o+x` на папку = право прохода, не чтения** — `o+x` даёт другим пользователям право *пройти сквозь* папку, но не *смотреть список файлов*. Это безопасно: `www-data` может зайти в `/root/PC_Shop/media/`, но не может сделать `ls /root/`.
- **`chmod o+rX` (заглавная X)** — `r` = чтение файлов, `X` = execute только для папок (право прохода), файлам execute не даётся. Это правильно: CSS-файл не должен быть «исполняемым».
- **`curl -I` — диагностика без браузера** — показывает HTTP-заголовки ответа (код статуса, Content-Type, размер). Быстрее и точнее, чем открывать браузер: сразу видно 200/403/404/500.
- **Порядок запуска сервисов** — после перезагрузки Gunicorn стартовал на секунду раньше Nginx (10:29:06 vs 10:29:07). Это правильно: «фабрика» (Gunicorn) должна быть готова до того, как «витрина» (Nginx) начнёт отправлять запросы.
- **Симлинк ≠ копия** — `ln -s` создаёт ярлык, а не копию файла. Удаление симлинка из `sites-enabled/` отключает сайт, но файл в `sites-available/` остаётся. Это механизм «включить/выключить» сайт в Nginx.
